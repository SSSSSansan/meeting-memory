# NetworkX против Neo4j: что измерили (для разделов 6 и 7 отчёта)

Один и тот же граф встреч (14 встреч, 64 узла, 172 ребра) и четыре сценария, реализованные трижды: обходом в Python без индексов, обходом в Python со словарями-индексами и запросом на Cypher. Граф размножали непересекающимися копиями ×10, ×100, ×1000 (до 64 000 узлов и 172 000 рёбер). Запросы всегда про копию 0, поэтому в S1 и S2 размер ответа постоянный, а в S3 и S4 растёт вместе с графом. Результаты всех трёх реализаций совпали на всех сценариях и размерах. Сырые цифры: `results/graph_engines.json`, код: `scripts/neo4j/bench_engines.py`. Замер на Mac выполнила Panda, 2026-11-14.

Сценарии: S1 цепочка замен решения, S2 в каких проектах человеку что поручено, S3 все пары противоречий, S4 открытые и просроченные задачи на дату.

Что учитывать при чтении:
- **Neo4j идёт по сети.** Каждый запрос — обращение по bolt в Docker, около 2–4 мс минимум, а NetworkX работает в памяти. Поэтому на малых графах разница в сотни и тысячи раз — это в основном накладные расходы, а не работа с данными.
- **В Neo4j были индексы** по `Node(nid)` и `Decision(project)`. Индекса по типу и статусу не было, поэтому S4 в Neo4j (58 мс на 64 000 узлов) перебирает все узлы и завышена. Остальные три сценария индекса по этим полям не требуют.
- **Холодный замер** (один первый запуск) в JSON есть, но по-настоящему холодным можно считать только ×1: Neo4j там 40–194 мс против 3–5 мс в прогретом состоянии. На ×10 и дальше сервер уже прогрет предыдущими масштабами.
- **Индекс NetworkX** строится один раз: 55.8 мс на 64 000 узлов (в таблице не учтён). Без индекса NetworkX перебирает узлы и рёбра.
- Среднее не считали, только медиану.

## Стоимость входа

| | NetworkX | Neo4j |
|---|---|---|
| установка с нуля | `pip install networkx`, секунды | Docker + образ: 25.4 с на `docker compose up -d` (24.7 с скачивание) и ≈ 30 с ожидания готовности, плюс `pip install neo4j` |
| нужен интернет | только для установки | для скачивания образа |
| состояние в репозитории | да, `data/graph/graph.json` | нет, данные в томе Docker, граф надо загружать скриптом (2.4 с на 64 узла, 6.7 с на 64 000) |
| построение с нуля | 0.1 мс на 64 узла, 0.6 с на 64 000 | см. строку выше |

## Выводы строго по данным

- До 64 000 узлов NetworkX со словарями-индексами отвечает быстрее Neo4j во всех четырёх сценариях, от ×56 (S4 на 64 000 узлов) до ×3900 (S3 на 64 узлах).
- NetworkX без индексов тоже быстрее Neo4j почти везде. Единственная точка, где Neo4j оказался быстрее, — S3 на 64 000 узлов: 12 мс против 24 мс у NetworkX без индекса. С индексом NetworkX на том же размере отвечает за 0.05 мс.
- Точки, после которой Neo4j выигрывает у NetworkX с индексом, в измеренном диапазоне нет.
- На миллионах узлов мы не мерили, экстраполяций не делаем.
- Преимущества Neo4j не в скорости: хранение на диске, одновременный доступ нескольких пользователей, браузер для визуального разбора графа, граф больше памяти.

## Рекомендация для Scribal

Тысячи встреч дадут сотни тысяч узлов: в наших замерах это на порядок выше 64 000, а граф такого размера всё ещё помещается в память одной машины. Поэтому переезд на Neo4j оправдан не скоростью, а многопользовательским доступом и хранением. Пока пользователь один и граф помещается в память, NetworkX проще и в наших замерах быстрее.

## Ограничения замера

- Граф синтетический, размножен копиями с той же структурой связей; реальные большие графы могут иметь другую форму.
- Neo4j в Docker на ноутбуке, сессия драйвера на каждый запрос; серверная конфигурация и пул соединений дали бы другие цифры.
- Нет индекса Neo4j по типу и статусу (см. выше). Перезамер только S4 с этим индексом: `python scripts/neo4j/bench_engines.py --engine both`, скрипт уже создаёт индекс.
- Python-реализации сценариев писались без оптимизации, кроме индексного варианта.
