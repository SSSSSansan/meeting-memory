# Извлечение: от транскрипта до графа (B11)

Как из реплик Scribal получаются решения, задачи и связи между ними. Все примеры взяты из реального графа `data/graph/graph.json` (14 встреч, 60 узлов, 158 рёбер).

## Поток

```
transcript.json + meeting.json → ingest → extract (LLM) → resolve → link (LLM) → граф NetworkX
                                                              └→ closes (LLM, отдельный проход)
```

| Этап | Код | Модель | Что делает |
|---|---|---|---|
| ingest | `src/ingest/` | нет | Scribal JSON → канонический транскрипт: `ts` = `HH:MM:SS`, имена говорящих по `speaker_names` и участникам |
| extract | `src/extract/` | да | решения, задачи, открытые вопросы с дословной цитатой |
| resolve | `src/resolve/entities.py` | нет | «Жол» / «проект Zhol» → один узел |
| link | `src/graph/link.py` | да | связи между решениями: supersedes, contradicts, refines, depends_on |
| граф | `src/graph/builder.py` | нет | узлы и рёбра, статусы решений вычисляются по рёбрам |
| closes | `src/graph/closes.py` | да | задача закрыта более поздним высказыванием |

## Что извлекаем

- **Решение**: зафиксированный выбор, меняющий план (срок, объём, ответственный, подход). Нужно, чтобы его произнесли и с ним согласились. Предложение «может, перенесём?» решением не считается. Определение лежит в `data/gold/what_is_a_decision.md` и совпадает с промптом.
- **Задача**: конкретное действие, у которого есть исполнитель и, возможно, срок. Личное «я сделаю до пятницы» это задача, а не решение.
- **Открытый вопрос**: поднят и не закрыт на этой встрече.

Промпт: [`src/extract/prompts.py`](../src/extract/prompts.py): `SYSTEM_PROMPT` (определения, 12 правил, пример, формат ответа) и `user_prompt(...)`. Полный текст читать там, он не дублируется в документе. Одна встреча — один запрос, `temperature=0`, ответ — JSON.

### Как режется транскрипт перед извлечением

Никак: встреча уходит в модель целиком одним запросом. Каждый сегмент Scribal остаётся отдельной репликой, строка вида `[00:09:37] Имя: текст` (таймкод от начала встречи и имя говорящего после определения имён, иначе `SPEAKER_XX`). Реплики не склеиваются и не режутся по окнам. К тексту добавляются название встречи, дата, день недели и список участников: по ним модель считает относительные сроки («к пятнице») и сопоставляет имена. На наших 14 встречах запрос занимает примерно 3600–6500 токенов на входе, поэтому встреча помещается целиком. Для очень длинных встреч нарезки в коде нет. Окно из трёх реплик существует только в baseline (чанки для поиска), на извлечение оно не влияет.

## Три защиты от выдумок

1. **Цитата дословная.** `source.quote` обязана быть подстрокой транскрипта после `normalize` (NFC, нижний регистр, схлопнутые пробелы; одна функция для всех, в том числе для казахских букв). Если цитата не нашлась, запрос повторяется один раз; пункт, у которого цитата не нашлась и после повтора, отбрасывается.
2. **Таймкод проверяется по тексту.** Если модель назвала не тот `ts`, он исправляется по реплике, где цитата найдена.
3. **Срок `due` принимается только если он однозначно следует из слов и даты встречи**, иначе `null`. Пустой список лучше выдуманной записи.

Метрики на gold: precision 0.86, recall 0.95, выдуманных цитат 0% (отчёт по прогонам: `runs/extract_report.jsonl`, команда `scripts/validate_extraction.py`).

## Пример на реальных данных: как меняется срок релиза Zhol

Три решения из трёх встреч (цитаты дословные):

| id | встреча, дата | решение | цитата |
|---|---|---|---|
| `d_m001_01` | m_001, 2026-08-03 | Выход в прод Zhol — 15 сентября | «ну тогда пятнадцатое сентября, и давайте уже без переносов» |
| `d_m006_01` | m_006, 2026-08-24 | Релиз переносится на 6 октября | «релиз Zhol переносится на пятого октября, нет, не пятого, шестого. шестого октября вместо пятнадцатого сентября» |
| `d_m011_01` | m_011, 2026-09-21 | Релиз переносится на 10 ноября | «поэтому релиз Zhol переносится на десятое ноября вместо шестого октября» |

Во втором случае говорящий оговорился и сам исправился; в `statement` попало исправленное «шестое», а цитата осталась как сказано. Так и должно быть: проверяется цитата, а не пересказ.

`link` сравнил пары решений одного проекта из разных встреч и поставил два ребра `SUPERSEDES` с `confidence` 0.9: `d_m006_01 → d_m001_01` и `d_m011_01 → d_m006_01`. Статус решения не вводится вручную, `compute_statuses` выводит его из рёбер: `d_m001_01` и `d_m006_01` становятся `superseded`, `d_m011_01` остаётся `active`.

## Связи (link)

Кандидаты не ищутся эмбеддингами: на 14 встречах дешевле перебрать все пары решений одного проекта из разных встреч (полная версия B5 не делалась). Для межпроектных пар есть ручное `--extra`. Модель выбирает тип из `supersedes | contradicts | depends_on | refines | same_topic | none`; в граф попадает связь с `confidence ≥ 0.6`, остальное лежит в `links_rejected.json` с причиной. Сейчас принято 8 связей, отклонено 42. Пример противоречия: `d_m008_02` («Николай занимается хотфиксом Zhol 14–18 сентября») против `d_m007_01` («Николай полностью работает на Squad с 14 по 18 сентября»). Это пара из разных проектов, поэтому её дают через `--extra`.

## Закрытия (closes)

Отдельный проход по открытым задачам и вопросам, без повторного извлечения. Для каждой задачи лексически выбираются до 5 реплик поздних встреч того же проекта (не больше двух с одной встречи), модель отвечает одним JSON: закрыто или нет, номер реплики, цитата. Цитата проверяется так же, как при извлечении. Если рядом по времени в той же встрече уже есть извлечённый пункт («Миграция БД выполнена»), он становится источником ребра `CLOSES`; иначе создаётся задача `t_<встреча>_cNN` со статусом `done`.

Эталон закрытий (`data/gold/closures.json`, 6 штук) в промпты и отбор не попадает. Его читает только `src/graph/eval_closes.py`, чтобы посчитать precision/recall отдельной строкой. На момент написания платный прогон ещё не выполнен, поэтому цифр качества здесь нет.

## Известные ограничения

- **81% реплик остаются без имени** (`SPEAKER_XX`): имена берутся из `speaker_names` и участников, а там, где они не определяются, метка остаётся. Вопросы про исполнителей от этого страдают, причём у baseline и у графа по-разному (граф получает имя из поля `owner`).
- **Проект пункта может быть определён неверно**: `t_m015_01` записан в Zhol, хотя говорится о Squad. Мы не правим это вручную, чтобы не подгонять метрики извлечения.
- **Связи между решениями не ищутся по смыслу через эмбеддинги**: пара из разных проектов без `--extra` не будет найдена.
- Корпус синтетический; цифры на реальных встречах Scribal могут отличаться.

## Стоимость

Из `runs/calls.jsonl` (пересчёт по токенам, `results/indexing_cost.json`): извлечение ≈ $0.014 на встречу (gpt-4o), связывание ≈ $0.0003 на встречу, закрытия ≈ $0.0001 (оценка). Индекс baseline на тех же встречах: ≈ $0.0001 (только эмбеддинги).

## Как воспроизвести

```bash
python -m src.pipeline --input data/raw --batch-size 5     # весь поток батчами
python scripts/validate_extraction.py                      # схема, цитаты, hallucination rate
python -m src.graph.link                                   # связи
python -m src.graph.closes --dry-run                       # закрытия без модели: кандидаты и оценка стоимости
```
