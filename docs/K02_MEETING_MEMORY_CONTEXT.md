| Поле | Значение |

| Направление | Engineering & AI |

### Бизнес-проблема

Важные решения распределены между несколькими встречами. Внутри одной встречи может обсуждаться несколько проектов. Руководитель хочет понимать: как менялись договорённости, какие задачи ещё открыты, что было решено ранее.

Пример: встреча называется «Закрытие проекта X». Система должна поднять прошлые договорённости именно по проекту X. При этом если на встрече по X обсуждался проект Y, эта информация должна попасть и в контекст проекта Y.

### Что должно работать (чек-лист заказчика)

1. Загружаем 10–15 тестовых транскриптов разных встреч.
2. Извлекаем проекты, задачи, решения, ответственных и сроки.
3. Связываем повторяющиеся сущности между встречами.
4. Отображаем связи в графе или простой таблице.
5. Задаём вопрос: «Что решили по проекту X за последние три встречи?»
6. Получаем ответ со ссылками на встречи и исходные фрагменты.
7. Видим конфликты и изменения решений.

### Критерии оценки

Заказчик явно называет: **token usage и бизнес-ценность**, точность связей, корректность источников, выявление противоречий, отсутствие выдуманных решений.

Отдельное требование: **проверить, даёт ли GraphRAG измеримое преимущество перед обычным RAG** на вопросах о нескольких встречах и проектах. Если качество не растёт — обосновать, почему обычного RAG достаточно. Отрицательный результат с цифрами засчитывается.

Общая шкала конкурса: 25% бизнес-ценность · 25% работающий результат · 20% проверяемое качество · 15% интеграция · 10% эффективность · 5% защита.

### Формат сдачи

- GitHub-репозиторий и README с шагами запуска.
- Демо-видео 3–5 минут.
- Результаты тестирования и таблица с метриками.
- Краткий отчёт о пользе, стоимости, ограничениях и возможном внедрении.

### Данные

Только собственные, открытые или синтетические. Защищённые клиентские материалы недоступны. Значит — генерируем синтетические истории проектов, где одна договорённость меняется от встречи к встрече, а отдельные встречи затрагивают сразу два проекта.

## 2. Ключевое решение по проекту

Главный сдаваемый результат — не «система памяти», а **честное сравнение двух архитектур на одних данных**:

- **Baseline RAG** — векторный поиск по чанкам сырых транскриптов → LLM отвечает.
- **GraphRAG** — LLM извлекает структуру, строится граф сущностей и связей, поиск идёт по графу, в LLM уходит подграф.

Обе ветки работают через один интерфейс и оцениваются одним набором вопросов. Это закрывает сразу 20% «проверяемое качество» и 10% «эффективность», и даёт готовый сюжет для отчёта и защиты.

**Рабочая гипотеза, которую проверяем:** GraphRAG выигрывает на вопросах, требующих обхода нескольких встреч и проектов (эволюция решения, противоречия, кросс-проектные связи), и не даёт выигрыша на простых фактических вопросах внутри одной встречи — при этом стоит дороже на этапе индексации.

Если гипотеза подтвердится — это и есть вывод для бизнеса: «включайте граф только на таких-то типах вопросов».

### Почему NetworkX, а не Neo4j

На 15 встречах граф будет порядка сотен узлов. NetworkX — это библиотека, никакого сервера, запускается у всех троих одинаково, сериализуется в JSON и коммитится в репозиторий. Neo4j добавит день на инфраструктуру и ничего не даст на таком объёме. В README это нужно явно обосновать — заказчик сам даёт NetworkX в списке рекомендованных.

### Нужен ли LangGraph

Для основного пайплайна — нет. Извлечение и связывание это линейный процесс, LangGraph добавит слой абстракции там, где нужен точный контроль над промптами и подсчётом токенов. Берите его только если останется время на вариант «agentic GraphRAG» с перезапросом (день 7+).

Langfuse — опционально, но если подключите, подсчёт token usage и трассировка приедут бесплатно, а это прямой критерий оценки. Альтернатива: свой декоратор, который пишет каждый вызов LLM в `runs/*.jsonl`. Второе быстрее и надёжнее, рекомендую его.

## 4. Контракты данных (не менять без согласования всех троих)

Это главный артефакт дня 0. Пока схема не зафиксирована, трое не могут работать параллельно.

### 4.1 Входной транскрипт — `data/transcripts/m_001.json`

```json
{
  "meeting_id": "m_001",
  "title": "Еженедельный статус — Атлас",
  "date": "2026-02-03",
  "participants": ["Айгерим Нурланова", "Руслан Ким", "Дана С."],
  "segments": [
    {
      "ts": "00:04:12",
      "speaker": "Руслан Ким",
      "text": "Давайте тогда перенесём релиз на двадцатое апреля, раньше не успеваем по миграции."
    }
  ]
}
```

### 4.2 Результат извлечения — `data/extracted/m_001.json`

```json
{
  "meeting_id": "m_001",
  "projects_discussed": ["Атлас", "Горизонт"],
  "decisions": [
    {
      "id": "d_m001_01",
      "project": "Атлас",
      "statement": "Релиз переносится на 20 апреля",
      "made_by": "Руслан Ким",
      "confidence": 0.92,
      "source": { "ts": "00:04:12", "quote": "давайте тогда перенесём релиз на двадцатое апреля" }
    }
  ],
  "tasks": [
    {
      "id": "t_m001_01",
      "project": "Атлас",
      "statement": "Подготовить скрипт миграции БД",
      "owner": "Айгерим Нурланова",
      "due": "2026-02-10",
      "status": "open",
      "source": { "ts": "00:06:40", "quote": "..." }
    }
  ],
  "open_questions": [
    {
      "id": "q_m001_01",
      "project": "Горизонт",
      "statement": "Кто выделит второго бэкендера на Горизонт",
      "source": { "ts": "00:21:05", "quote": "..." }
    }
  ]
}
```

Правила:
- `id` формируется как `<тип>_<meeting_id>_<порядковый номер>` — детерминированно, чтобы прогоны были воспроизводимы.
- `source.quote` — **дословная подстрока** из транскрипта. Если модель перефразировала, запись считается невалидной (это проверяется автоматически, см. 4.5).
- `due` — ISO-дата или `null`. Относительные сроки («к следующей пятнице») резолвятся от `date` встречи на этапе post-processing, не в промпте.
- `project` — строка как она прозвучала. Нормализация — задача шага resolve, не extract.

### 4.3 Связи — `data/graph/links.json`

```json
{
  "from": "d_m012_01",
  "to": "d_m001_01",
  "type": "supersedes",
  "confidence": 0.86,
  "rationale": "Новое решение переносит ту же дату релиза Атласа с 20 апреля на 5 мая"
}
```

Допустимые `type`:

| Тип | Когда ставится |
|---|---|
| `supersedes` | то же самое решение принято заново с другим содержанием |
| `contradicts` | два действующих решения несовместимы (например, один и тот же человек выделен на два проекта в одно время) |
| `depends_on` | решение выполнимо только при условии другого |
| `refines` | уточняет детали ранее принятого, не отменяя его |
| `same_topic` | про одно и то же, но без логической связи |

Порог записи в граф: `confidence >= 0.6`. Всё ниже — в `links_rejected.json` для отчёта (полезно показать на защите).

### 4.4 Граф

Узлы: `Meeting`, `Project`, `Person`, `Decision`, `Task`, `OpenQuestion`.

Рёбра:
- `Decision -[BELONGS_TO]-> Project`
- `Decision -[STATED_IN]-> Meeting`
- `Decision -[SUPERSEDES|CONTRADICTS|DEPENDS_ON|REFINES]-> Decision`
- `Task -[ASSIGNED_TO]-> Person`
- `Task -[IMPLEMENTS]-> Decision`
- `Meeting -[DISCUSSES]-> Project`
- `Person -[PARTICIPATED_IN]-> Meeting`

Статус решения вычисляется, а не хранится вручную: решение `superseded`, если на него есть входящее ребро `SUPERSEDES`, иначе `active`.

Сериализация: `data/graph/graph.json` через `networkx.node_link_data`.

### 4.5 Автоматическая валидация извлечения

Скрипт `scripts/validate_extraction.py` проверяет на каждом файле:
1. JSON соответствует схеме (pydantic-модели в `src/schemas.py`).
2. Каждый `source.quote` реально встречается в тексте своей встречи (нормализация: lowercase, схлопывание пробелов). Это защита от выдуманных решений — прямой критерий заказчика.
3. Все `project` из `decisions`/`tasks` присутствуют в `projects_discussed`.
4. Нет дублей `id`.

Процент записей, проваливших проверку 2, идёт в отчёт как **hallucination rate**. Это одна из самых сильных цифр для защиты.

### 4.6 Единый интерфейс ответа

Обе ветки (baseline и graph) возвращают одну структуру:

```json
{
  "answer": "Срок релиза Атласа менялся дважды...",
  "citations": [
    { "meeting_id": "m_001", "ts": "00:04:12", "quote": "..." },
    { "meeting_id": "m_012", "ts": "00:09:30", "quote": "..." }
  ],
  "mode": "graph",
  "usage": { "prompt_tokens": 2140, "completion_tokens": 180, "cost_usd": 0.0004 },
  "latency_ms": 1830
}
```

Это позволяет оценивать обе ветки одним кодом.

## 5. Два варианта реализации LLM

Весь код ходит в модель только через `src/llm_client.py` с интерфейсом:

```python
def complete(messages: list[dict], *, json_schema: dict | None = None, temperature: float = 0.0) -> LLMResponse
def embed(texts: list[str]) -> list[list[float]]
```

Переключение — переменной `LLM_BACKEND=openai|local` в `.env`. Никакой другой файл не должен знать, какой backend активен. Это одновременно и правильная архитектура, и готовый пункт для отчёта: «мы померили оба».

### Вариант A — OpenAI (мини-модели)

| Компонент | Что брать |
|---|---|
| Извлечение, связывание, ответы | `gpt-4o-mini` или `gpt-4.1-mini` |
| Эмбеддинги | `text-embedding-3-small` |
| LLM-судья для оценки | та же мини-модель |

Плюсы: ноль инфраструктуры, стабильный structured output, токены считаются самим API, воспроизводится у любого члена команды за 5 минут.

Минусы: стоит денег, зависимость от сети, данные уходят наружу (для Scribal с клиентскими встречами это реальное возражение — упомяните в отчёте).

Оценка расхода: 15 транскриптов × ~8k токенов + связывание + ~60 вопросов × 2 ветки × 3 прогона. Это единицы долларов на мини-моделях при аккуратной работе. **Перед стартом сверьте актуальные цены на странице OpenAI** — модели и тарифы меняются.

Контроль бюджета обязателен: `scripts/cost_guard.py` ведёт счётчик в `runs/budget.json` и падает с ошибкой при превышении лимита из `.env`. Без этого легко сжечь бюджет одним циклом с багом.

### Вариант B — локально на GPU-сервере

| Компонент | Что брать |
|---|---|
| Извлечение, связывание, ответы | открытая instruct-модель уровня 7–14B через vLLM (семейство Qwen работает хорошо на русском) |
| Эмбеддинги | `BAAI/bge-m3` — мультиязычная, нужна для русского и казахского |
| Реранкер (опционально) | `BAAI/bge-reranker-v2-m3` |
| Сервинг | vLLM с OpenAI-совместимым endpoint |

Плюсы: бесплатно, нет лимитов на число прогонов (можно гонять ablation сколько угодно), сильный аргумент про приватность данных встреч, видно реальную задержку на своём железе.

Минусы: день на поднятие сервинга, structured output менее стабильный (нужен retry-цикл и грамматики/`guided_json` в vLLM), качество связывания на русском может просесть.

vLLM поднимается с OpenAI-совместимым API, поэтому `llm_client.py` отличается только `base_url` и именем модели. **Проверьте актуальные версии моделей на Hugging Face** — названия быстро устаревают.

### Рекомендуемая комбинация

Гибрид, и это само по себе результат для отчёта:

- Генерация синтетических транскриптов — **локально** (объёмно, качество не критично, правится руками).
- Извлечение и связывание по всем 15 встречам, все отладочные прогоны — **локально**.
- Финальные замеры качества ответов и LLM-судья — **OpenAI мини**, чтобы цифры были воспроизводимы у проверяющего.
- Отдельная таблица в отчёте: «то же самое на локальной модели» — качество, задержка, стоимость владения.

Так бюджет остаётся почти нетронутым, а в отчёте появляется второе сравнение, которого никто другой не сделает.

## 6. Роли

Деление по вертикалям, а не по слоям — каждый владеет своей частью от начала до конца и отвечает за свой кусок метрик. Заказчик на установочной встрече отдельно просил видеть, кто что сделал и какой вклад принёс, поэтому роли фиксируются в README.

### Роль A — Данные и оценка

Владеет: `data/transcripts/`, `data/gold/`, `src/eval/`, итоговый отчёт.

1. Сгенерировать 12–15 транскриптов по 3–4 проектам с заложенными ситуациями (см. 7.1).
2. Руками разметить gold-set: какие решения/задачи должны быть извлечены, какие пары связаны и каким типом.
3. Составить 50–60 вопросов пяти типов (см. 7.2) с эталонными ответами и списком встреч-источников.
4. Собрать eval-harness: прогон обеих веток, метрики, таблицы, графики.
5. Откалибровать LLM-судью на 30 размеченных вручную примерах и указать его согласованность с человеком в отчёте.
6. Написать итоговый отчёт: польза, стоимость, ограничения, внедрение.

Это самая недооценённая роль и одновременно та, от которой зависят 20% оценки. Нужен человек, аккуратный с данными.

### Роль B — Извлечение и граф

Владеет: `src/extract/`, `src/resolve/`, `src/graph/`.

1. Промпт и pydantic-схемы извлечения, retry-цикл на невалидный JSON.
2. Разрешение сущностей: «Атлас», «проект Атлас», «атлас» → один узел. Нормализация + эмбеддинги + LLM на спорных случаях.
3. Генерация кандидатов на связи (эмбеддинг-поиск по решениям того же и смежных проектов) и классификация типа связи через LLM.
4. Сборка графа NetworkX, вычисление статусов, сериализация.
5. `validate_extraction.py`.
6. Замер: сколько токенов стоит индексация одной встречи.

Самая технически содержательная часть — здесь живёт то, чего нет в baseline.

### Роль C — Поиск, ответы, приложение

Владеет: `src/retrieval/`, `src/answer/`, `app/`.

1. Baseline RAG: чанкование, векторный индекс, top-k поиск.
2. GraphRAG retrieval: от вопроса к сущностям → обход графа → сборка подграфа в контекст.
3. Генерация ответа с обязательными цитатами и таймкодами, единый формат из 4.6.
4. Streamlit: загрузка транскрипта, таймлайн решений по проекту, визуализация графа, Q&A с подсветкой источников, переключатель baseline/graph (сильный ход на демо).
5. Логирование токенов и задержки по каждому запросу.
6. Демо-видео 3–5 минут.

### Кому что

Если у тебя бэкенд-опыт и ты уже делала RAG — бери **B**. Граф и связывание это ядро проекта и самая заметная часть на защите, а retrieval в роли C ты и так знаешь, там будет меньше нового. Роль C логична для того, кто сильнее во фронте и демо. Роль A — самому дисциплинированному с данными.

### Что делать, чтобы не блокировать друг друга

День 0 заканчивается тем, что в репозитории лежат:
- `src/schemas.py` с pydantic-моделями из раздела 4;

## 7. Данные

### 7.1 Что обязательно заложить в синтетику

Без этих ситуаций нечего измерять — граф будет выглядеть одинаково с baseline:

1. **Эволюция решения.** Срок релиза переносится трижды на разных встречах. Проверяет `supersedes` и вопросы типа «как менялось».
2. **Кросс-проектная встреча.** Встреча называется «Атлас», но 10 минут обсуждают «Горизонт». Это прямо из описания заказчика, обязательный кейс.
3. **Противоречие.** Один человек выделен на два проекта в одну и ту же неделю на разных встречах. Проверяет `contradicts`.
4. **Забытое обещание.** Задача выдана на встрече 3, срок прошёл, на встречах 4–8 не упоминается. Проверяет «что ещё открыто».
5. **Разные написания сущностей.** «Айгерим», «Айгерим Н.», «Аигерим» — один человек. Проверяет resolve.
6. **Отменённое решение.** Принято, затем явно отменено без замены.
7. **Шум.** Светская беседа, перебивания, «эээ», оговорки, самоисправления («нет, не двадцатого, двадцать первого»). Слишком чистые транскрипты дают нереально высокое качество, и это видно проверяющему.
8. **Смена языка.** Вставки на казахском и английском внутри русской речи — реальность Scribal и повод для отдельного среза в отчёте.

Структура: 3–4 проекта, 12–15 встреч, хронология за 2–3 месяца, 4–6 постоянных участников. Генерировать по одному проекту за раз, задавая LLM сюжетную линию, затем править руками.

Каждый заложенный кейс фиксируется в `data/gold/scenarios.md` — это и разметка, и сценарий для демо-видео.

### 7.2 Типы вопросов для оценки

| Тип | Пример | Ожидание |
|---|---|---|
| T1 — факт из одной встречи | «Кто отвечает за миграцию БД?» | baseline справляется, граф не нужен |
| T2 — эволюция во времени | «Как менялся срок релиза Атласа?» | граф должен выигрывать |
| T3 — кросс-проектный | «Что решали по Горизонту на встречах про Атлас?» | граф должен выигрывать сильно |
| T4 — противоречия | «Есть ли конфликты по загрузке людей?» | baseline почти не справляется |
| T5 — открытые пункты | «Что по Атласу ещё не закрыто?» | граф должен выигрывать |

По 10–12 вопросов каждого типа. Разбивка по типам в итоговой таблице — главный результат проекта.

## 8. Метрики

| Группа | Метрика | Как считается |
|---|---|---|
| Извлечение | precision / recall / F1 по решениям и задачам | против gold-set, совпадение по смыслу через LLM-судью с ручной проверкой выборки |
| Извлечение | hallucination rate | доля записей, чья цитата не найдена в транскрипте (автоматически) |
| Resolve | accuracy кластеризации сущностей | доля верно схлопнутых проектов/людей |
| Связи | precision / recall по каждому типу | против размеченных пар |
| Ответы | accuracy | LLM-судья + ручная проверка 30 примеров, согласованность указать |
| Ответы | citation correctness | доля ответов, где указанные встречи совпадают с эталонными |
| Ответы | hallucinated decisions | доля ответов, упоминающих решения, которых нет в gold |
| Стоимость | токены индексации | на одну встречу, prompt + completion |
| Стоимость | токены на вопрос | по типам вопросов, обе ветки |
| Стоимость | $ и задержка | на вопрос, обе ветки |

Все прогоны повторять 3 раза, в таблице показывать среднее и разброс. Один прогон ничего не доказывает, и на защите об этом спросят.

**Итоговая таблица проекта** — accuracy baseline vs graph в разрезе T1–T5, рядом стоимость и задержка. Один экран, который отвечает на главный вопрос задания.

## 11. Промпты (черновики, дорабатывать по результатам)

### 11.1 Извлечение

```
Ты извлекаешь структурированную информацию из транскрипта рабочей встречи.

ВХОД: транскрипт с таймкодами и именами говорящих.
ВЫХОД: только JSON по указанной схеме, без пояснений.

Правила:
1. РЕШЕНИЕ — это зафиксированный выбор, который меняет план работы:
   сроки, объём, ответственный, подход, бюджет, отмена ранее принятого.
   НЕ решение: предложение без согласия, вопрос, размышление вслух,
   пересказ того, что уже было решено раньше.
2. ЗАДАЧА — конкретное действие с исполнителем или без него.
3. ОТКРЫТЫЙ ВОПРОС — явно поднятый и явно не закрытый на этой встрече.
4. В поле source.quote копируй ДОСЛОВНЫЙ фрагмент транскрипта,
   по которому ты сделал вывод. Не перефразируй. Не сокращай до неузнаваемости.
5. Если на встрече обсуждалось несколько проектов — проставь каждому
   элементу тот проект, к которому он относится, даже если название
   встречи говорит о другом проекте.
6. confidence от 0 до 1: насколько явно это прозвучало.
   Ниже 0.5 — если приходится догадываться.
7. Сроки записывай как ISO-дату, если она однозначно выводится
   из даты встречи. Иначе null, а формулировку оставь в statement.
8. Ничего не придумывай. Пустой список лучше выдуманной записи.

Дата встречи: {date}
Название: {title}
Участники: {participants}

ТРАНСКРИПТ:
{transcript}
```

### 11.2 Классификация связи

```
Два решения из разных встреч одного или смежных проектов.
Определи отношение между ними.

РЕШЕНИЕ A (встреча {date_a}, проект {project_a}):
{statement_a}

РЕШЕНИЕ B (встреча {date_b}, проект {project_b}, более раннее):
{statement_b}

Типы:
- supersedes: A принимает тот же вопрос заново и меняет содержание B
- contradicts: A и B оба действуют, но несовместимы друг с другом
- depends_on: A выполнимо только при условии B
- refines: A уточняет детали B, не отменяя его
- same_topic: про одно и то же, но логической связи нет
- none: связи нет

Верни JSON: {"type": "...", "confidence": 0.0-1.0, "rationale": "одно предложение"}

Будь строг. none и same_topic — нормальные ответы.
Ставь supersedes только если это буквально тот же вопрос, а не похожая тема.
```

### 11.3 Ответ (обе ветки, одинаковый)

```
Ответь на вопрос, опираясь ТОЛЬКО на приведённый контекст.

Правила:
1. Каждое утверждение о решении или задаче подкрепляй ссылкой
   на встречу и таймкод.
2. Если решение менялось — покажи хронологию, а не только последнее
   состояние.
3. Если в контексте есть противоречащие друг другу решения — укажи
   это явно, не выбирай одно.
4. Если ответа в контексте нет — так и скажи. Не достраивай.

Формат ответа: JSON с полями answer (текст) и citations
(список {meeting_id, ts, quote}).

ВОПРОС: {question}

КОНТЕКСТ:
{context}
```

## 12. Риски и что с ними делать

| Риск | Что делать |
|---|---|
| Синтетика слишком чистая, качество нереально высокое | Шум, перебивания, самоисправления, смена языка. Проверяющий это заметит сразу. |
| Разные люди по-разному размечают «решение» | `what_is_a_decision.md` в день 0, разметку делает один человек (роль A). |
| Связей находится слишком много, граф превращается в кашу | Порог confidence, ограничение кандидатов по проекту и временному окну, отдельный файл отклонённых. |
| Граф не даёт выигрыша | **Это нормальный результат.** Заказчик явно разрешил его защищать. Покажите, на каких типах вопросов не даёт и почему, и во что обошлась индексация. |
| Не успеваем к дню 7 | Режьте в таком порядке: число встреч 15→10, число вопросов 60→40, Neo4j→NetworkX (сразу), визуализация графа→таблица. **Не режьте:** eval-harness и сравнение с baseline — это 20% оценки. |
| Бюджет улетает | `cost_guard.py` с жёстким лимитом, отладка на локальной модели, кэш ответов LLM по хэшу промпта в `runs/cache/`. |
| Структурированный вывод ломается на локальной модели | `guided_json` в vLLM, retry с показом ошибки валидации, fallback на OpenAI для проблемных встреч (и упомянуть это в отчёте). |
